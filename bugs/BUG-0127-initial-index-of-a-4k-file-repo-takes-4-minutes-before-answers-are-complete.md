## 原因・直し方・確認（2026-10-31）

### 原因

初回の索引の走査（`engine/indexer.Indexer._scan`）は 1 プロセスの中で、ファイルの解析（構文解析・シンボル・関係の抽出。GIL を握る
Python のコード）をスレッドで 1 ファイルずつ進め、書き込み（`IndexWriter` のスレッド。SQLite）を 1 バッチ先行させて重ねていた。
Mnemo の写し（`d419cf0b`、4,222 ファイル）を修正前のコード（`ee3b5c6`）で、台本から 1 回走査した内訳:

```
走査全体 246.2 s = ファイルの段 223.9 s + 関係の整え 15.3 s + 順位 7.0 s
  解析のスレッドの時間 152.8 s（うち関係の抽出 129.2 s）、書き手のジョブ 191.1 s（50 ファイルのバッチ 85 個。1 個 約 2.25 s）
重ねずに順に流すと: 解析だけ 124.6 s、書き込みだけ 74.7 s（同じ機で 57〜82 s）、整え 15.0 s、順位 6.7 s（合計 221 s）
```

- **重ねたほうが順に流すより遅い**（246 s > 221 s）。書き手は SQLite の小さな文を約 40 万回発行し（`execute` 405,229 回・
  `executemany` 15,845 回）、文ごとに GIL を手放して取り戻すたびに、解析のスレッドから切り替え間隔ずつ待たされていた（convoy。
  BUG-0112 の前景と背景の間と同じ現象が、背景の解析と書き手の間で起きていた）。
- **書き込みそのものも遅かった**: 書き手の接続のページキャッシュが SQLite の既定の 2 MiB で、長い URN の索引（`symbols` の `urn`・
  `name`、`relations` の `target_urn`）へばらばらの位置に差し込むたびにページを読み直していた（128 MiB にするだけで書き込み
  61〜82 s → 38〜42 s）。文の数も多かった: シンボルの INSERT と、そのシンボルを先に指していた行の `target_file_id` の UPDATE が
  シンボルごとに 1 文（65,824 × 2）、関係の目標の持ち主の `file_id` の SELECT と外部シンボルの `INSERT OR IGNORE`（＋既存なら
  SELECT）が目標ごとに 1 文（約 20 万）。
- **型サーバーの準備はさらに 20 秒前後**: 型サーバーは最初の要求で起こす（遅延起動）。ベンチは索引のジョブが済んでから `get_diagnostics`
  で起こすので、`lsp_ready_ms` は `index_ready_ms` の 20 秒前後後になっていた。

### 直し方（決めたこと）

1. **走査の解析を子プロセスに並べる**（`engine/analysis_pool.py`、`e90ec54`）。解析の要るファイルが `POOL_MIN_FILES`（64）を超えたら、
   残りを `spawn` の子プロセス（`ProcessPoolExecutor`）で `Indexer._analyze_sync` にかける。子の数は `LUCIANKE_INDEX_WORKERS`（0 で
   使わない）、無ければ論理 CPU の半分（最大 8。残りは LSP とツールの呼び出しに残す）。親は読み込み（`sha256` の照合）を済ませてから
   子に渡し、結果は**列挙の順に**受け取って 50 ファイルのバッチに積む（`file_id` の振り方・バッチの切れ目・取り込みの順は同じ
   プロセスで解析したときと同じ）。子 1 つあたり 8 ファイルまで先に渡す。ctags の外形（Tier 4）は親が作る。子が落ちた
   （`BrokenProcessPool`）・結果を渡せないときは、そのファイルから同じプロセスで解析する。小さな差分の走査は子を起こさない。
   子の標準出力は `bootstrap_io` の後に起こすので stderr に重なる（stdout は JSON-RPC のまま）。exe は `__main__` の
   `freeze_support` が子の起動を受ける。子の警告は出所つきで stderr に出し、`files` 行だけに落ちたファイルは親がログに書く（`417ce34`）。
   親の GIL を握るのは書き手と結果の受け取りだけになり、convoy も消える。
2. **書き手のページキャッシュを 128 MiB に**（`index/connection.WRITER_CACHE_KIB`。上限なので小さな DB では使った分だけ。`e90ec54`）。
3. **取り込みの文をまとめる**（`index/ingest.py`、`e90ec54`）: シンボルの INSERT と `target_file_id` の UPDATE を `executemany`、関係の
   目標の `file_id`（`_fill_symbol_files`）と外部シンボルの有無（`_ensure_externals`。昇格の規則は `_ensure_external` と同じ）を
   `IN (…)` でファイルごとに 1 文。書き込みだけで 25〜27 s（修正前 57〜82 s）。
4. **大きなワークスペースでは型サーバーを走査と並べて起こす**（`tools/_runtime.warm_type_server`、`ef5eb80`）。走査の列挙が
   `EAGER_LSP_MIN_FILES`（200）以上なら、型サーバーのある言語のうちファイルの最も多い 1 言語の型解決用（types の役。Lint 用は
   起こさない）を列挙の直後に起こす（待たない。`standby` でなければ何もしない。`Indexer.on_listed` が列挙を渡す）。小さな
   ワークスペースは従来どおり最初の要求で起こす。呼ぶ側の AI が参照・呼び出し階層を `exact` で使えるまでの時間を縮めるため
   （仕様書 §12.3 の遅延起動に例外を足した。全言語は立ち上げない MUST NOT はそのまま）。
5. **待たせない形（手 2）は既にある**ので変えていない: T-00 の `set_roots` / `reindex` は索引のジョブを投げてすぐ戻る（処理規約 6）、
   `status` の `jobs` に進み（%・`settling relations 3/170` などの段）、索引から答えるツールは得られた分で答えて `warnings[]` に進みを
   入れる（BUG-0070・BUG-0112）、対象のファイルは走査より先に取り込む（`ingest_ahead`）。ray の 120 秒は、索引のジョブの完了を待つ
   使い方で上限に当たっていたと読める（4,222 ファイルで約 1 分に縮んだ）。
6. 仕様書 §4.3.1・§4.4・§12.3・§12.7、設計書 §6.1・§6.2・§7.6.1・§7.6 の並列度・LSP の状態表・§9.3・R-6 を合わせた（`ef5eb80`）。

### 残ったこと

- 修正後のファイルの段は書き込みが律速（43.8 s のうち書き手 33.0 s）。残りは行そのものの B-tree の差し込み（`relations` 約 40 万行に
  索引 3 つ・`_name_calls` 約 13 万行に索引 3 つ）。初回の走査だけ索引を後から作る手は、走査の途中の読み（`_sync_symbols` の
  `target_urn` 引き・整え・途中のツールの答え）が索引に頼るので入れていない。
- 子の数の既定（論理 CPU の半分・最大 8）は、この機（論理 14）で決めた。2 コア以下の機は子を使わない（書き込みの改善だけ効く）。
- 先起こしした型サーバーは `ready` になっても、作業空間の解析は最初の参照・呼び出し階層の要求まで進まない（basedpyright は開いた
  文書から解析する。文書を開かなければ `ready` は進捗の終わりか、合図が無いときの 15 秒の代わりで立つ）。冷えた型サーバーへの最初の重い問い合わせ（T11）が予算に当たる回があるのは
  前後とも同じ。先起こしのときに中心のファイルを開いて解析を始めさせる手は入れていない。
