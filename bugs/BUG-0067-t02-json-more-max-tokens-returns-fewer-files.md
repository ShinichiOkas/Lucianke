# BUG-0067 get_file_skeleton の json で max_tokens を上げると返るファイル数が減る（F-PY: 6000 で 2 件、8000 で 1 件）

- 報告: 2026-10-31 / 見た人: BUG-0065 を直した役（F-PY の契約テストが 1 件しか返らない理由を測ったとき）
- 見たことだけを書く（調査していない。調査は直す役の仕事）

## 実測（作業ツリー = `b1ce8ac` + BUG-0065 の直し。F-PY〈httpx〉・`format: "json"`）

`get_file_skeleton {"paths": ["httpx/_urls.py", "httpx/_api.py"], "max_tokens": N}`:

| max_tokens | 返った items | `_urls.py` の `truncated_members` | `used_tokens_est` | `next_cursor` |
|---|---|---|---|---|
| 6000 | `_urls.py`・`_api.py` の 2 件 | 50（縮退） | 2,637 | なし |
| 8000 | `_urls.py` の 1 件だけ | 0（丸ごと） | 6,806 | あり（`_api.py` は次ページ） |
| 12000 | 2 件 | 0 | 8,824 | なし |

- 各ファイル単独（`max_tokens=50000`）の json の量: `_urls.py` 6,751、`_api.py` 2,199 トークン。
- 予算を 6000 → 8000 に上げると、返るファイルが 2 件 → 1 件に減り、6000 で返っていた `_api.py` が次ページに回る。
- BUG-0055 の省き方（`1e1a9aa`）を入れていたときは、同じ 2 ファイルで 6000 が 1 件・8000 が 2 件だった（量が変わると、どの予算で減るかが入れ替わる）。

## 手がかり（見たことだけ）

- 仕様書 §11 T-02 処理規約 8: 「予算に収まらないとき、ファイル内では `doc:` → `urn:` → 非公開メンバー → 入れ子メンバー（最上位は残す）の順に落とし、落とした件数を `- truncated: N members omitted` に書く。それでも収まらなければ残りのファイルを次ページに回す。」
- `tests/contract_fixtures/test_fx_read_T00_T08.py::test_t02_postcondition_1_2_5_skeleton_matches_the_source` は `max_tokens=6000` で 2 ファイルとも 1 ページに返ることを求めている。今これが通るのは、`_urls.py` が単独で 6000 に入らず縮退するから（BUG-0065 の票）。
- compact で同じことが起きるかは測っていない。

## 再現

上の呼び出しを `max_tokens` 6000・8000・12000 で、F-PY のワークスペース（`bench/.cache/httpx` の複製。`tests/contract_fixtures/_rig.py` の `open_rig("F-PY", …)`）に対して行う。

## 原因・直し方・確認（2026-10-31）

### 原因

- パッカー（`src/lucianke/mcp/budget.py` の `Packer.pack`）は先頭から丸ごと詰め、入らないレコードに `shrink` があれば縮退版を入れ、**その後ろにも詰め続けていた**。縮退で空いた分に後ろのレコードが入るのは予算が小さいときだけなので、予算を上げて先頭が丸ごと入ると、後ろが次ページに回って件数が減る。
- F-PY の 2 ファイルの実測（json の `data` の量。`levels` で各段を数えた）: `_urls.py` は丸ごと 6,627 → `doc:` 省略 6,325 → `urn:` 省略 6,324 → 入れ子省略 441（`truncated_members` 50。非公開の段は本文が前の段と同じで飛ぶ）と、最後の段だけが極端に小さい。`_api.py` は最も小さい段でも 2,033（入れ子が無い）。前置き（封筒）は 124。
  - 6000: `_urls.py` は丸ごとも浅い段も入らず 441 に縮み、空いた分に `_api.py` が丸ごと入って 2 件。
  - 8000: `_urls.py` が丸ごと入り、残り約 1,250 に `_api.py`（最小 2,033）が入らず次ページ。1 件。
  - 縮退の段の選び方（json の二分探索）は正しく、収まる最も浅い段を選んでいた。
- 同じ種類の単調でない所がもう 1 つあった（compact の要約。乱数の性質テストで見つけた）: 要約（`# summary:`）の分を丸ごと先に取り分け、1 件も入らないときだけ要約を省いて詰め直していた。要約つきで 1 件入る予算に上げると、要約なしで入っていた後ろのレコードを要約が押し出す（`max_tokens` を 2 上げて 11 件 → 1 件）。詰め直しは 1 周目の縮退の結果を使い回していたので、1 周目の狭い予算で `None` だった縮退を広い 2 周目でも試さなかった。

### 仕様の判断（師匠の規則 2026-10-31: 主な利用者は MCP で呼ぶ AI エージェント。仕様の問いはその利用者に最も役立つ形で決める）

- 旧仕様（§5.6-1「先頭から順に」、§11 T-02 規約 8、設計書 §7.2.2 の擬似コード）は、縮退版の後ろに詰めるかを決めておらず（擬似コードは詰め続ける形）、予算に対する単調性はどこにも無かった。
- 師匠の指示: 「`max_tokens` を上げた応答は、小さい予算の応答より情報が減らない（単調）。件数が減らないのが最低限、見えている内容も縮まないのが理想」。
- 決めたこと（仕様書 §5.6-5 を追加、§11 T-02 規約 8・設計書 §7.2.2・§7.4.4 を改訂）:
  1. 丸ごと入らない最初のレコードだけを縮退版にして **そのページの最後の 1 件** にし、後ろには詰めない（残りは `next_cursor` で次ページ）。ページは、予算に依らない固定の鎖「r0 の縮退版（浅い段ほど後）→ r0 丸ごと → r1 の縮退版 → r1 丸ごと → …」のうち、トレーラ込みで収まる最も先の形。鎖が予算に依らないので、件数も各レコードの版も予算について単調（理想のほうまで満たす）。T-05 の途中で切った本文（`resume`）は以前から最後の 1 件で、同じ規則に入る。
  2. 要約の取り分は、レコードに使える予算の 1/4 まで（`SUMMARY_SHARE_DIVISOR`）。長い要約は末尾を「…」で切る。取り分は予算 1 トークンにつき高々 1 トークンしか増えないので、レコードの取り分は減らない。ふつうの予算では要約は丸ごと入る（T-01・T-08 の要約の契約テストはそのまま通る）。
- 選ばなかった案と理由:
  - 幅優先（全レコードを最小の縮退版で入れてから先頭から詳しくする）: 1 回で全ファイルの概形が見えるが、縮退した分はカーソルで辿っても二度と返らない。深さ優先なら、次ページのファイルは丸ごとで返る（落ちるのは各ページの最後の 1 件の詳細だけ）。`resume` とも合わない。
  - 要約を常にレコードの後回しにする（残りに入るときだけ）: 1 件が小さいツール（T-03 など）で要約がほぼ消え、T-01 規約 4・T-08 規約 6（要約を出す）に反した（契約テスト 2 件が落ちた）。
  - 要約を常に丸ごと取り分ける（1 件も入らなくても省かない）: 単調だが、レコードが入る予算で 0 件と警告を返す。
- 代償: 縮退版の後ろに詰めていた分は次ページに回る。BUG-0067 の 2 ファイルは 6000 で `_urls.py` の最上位だけ（618 トークン）+ カーソル（次ページで `_api.py` が丸ごと返る）。
- 直した副作用: 編集ツール（T-10・T-13）は diff（ハンクで縮退）を診断（`added:` / `resolved:`）の前に置いていたので、新しい規則では diff が縮むと診断が次ページ（編集ツールのカーソルは辿れない）に回った（パッカー単体で、diff 958 トークン・`max_tokens` 400 / 800 で、以前は `[diff, added, resolved]`、変更後は `[diff]` + カーソル）。診断を先に・diff を最後に並べ替えた。仕様書の T-10 の compact の例も kv 行の直後に診断を置いている。

### 確認（2026-10-31）

`get_file_skeleton {"paths": ["httpx/_urls.py", "httpx/_api.py"], "format": "json", "max_tokens": N}`（F-PY）。items の括弧は `truncated_members`（`_urls.py` の 0* は `doc:` を省いた段。json では件数 0 のまま）:

| max_tokens | 直す前 items | 直す前 used / cursor | 直した後 items | 直した後 used / cursor |
|---|---|---|---|---|
| 2000 | `_urls`(50) | 618 / あり | `_urls`(50) | 618 / あり |
| 3000〜6000 | `_urls`(50)・`_api`(0) | 2,637 / なし | `_urls`(50) | 618 / あり |
| 6500 | `_urls`(50)・`_api`(0) | 2,637 / なし | `_urls`(50) | 618 / あり |
| 6550 | `_urls`(0*) | 6,503 / あり | `_urls`(0*) | 6,503 / あり |
| 7000〜8500 | `_urls`(0) | 6,806 / あり | `_urls`(0) | 6,806 / あり |
| 8800 | 2 件 | 8,781 / なし | 2 件 | 8,781 / なし |
| 9000〜50000 | 2 件 | 8,823〜8,824 / なし | 2 件 | 8,823〜8,824 / なし |

- 直す前は 2000 → 1 件、3000〜6500 → 2 件、7000〜8500 → 1 件、8800 以上 → 2 件（減る）。直した後は 1 件 → 2 件で減らない。各ファイルの版も `_urls.py` が 50 省略 → `doc:` 省略 → 丸ごと、`_api.py` が 無し → 丸ごとと縮まない。
- compact は同じ 2 ファイルで直す前後とも 2000・3000 が 1 件、4000 以上が 2 件（この組では変わらない）。
- パイプラインを通した細かい走査（T-02、F-PY の 5 ファイル `_urls`・`_api`・`_config`・`_exceptions`・`_status_codes`、`max_tokens` 300〜16000 を 13 刻み）: json・compact とも 1,208 予算で、件数の減少・ファイルの骨格行数の減少 0 件、`used_tokens_est <= max_tokens`。桁の境目（960〜1040、9960〜10040 を 1 刻み）でも 0 件。
- 残る注意（観測のみ）: パイプラインの前置き（`mcp/fit.py`）は `max_tokens` の桁数を含むので、10 の累乗をまたぐと前置きが 1〜2 トークン増え、レコードに使える予算が 1 減りうる。パッカーの単調性は前置きを固定したときの保証。上の境目の実測では違反は無かった。
