# BUG-0110 compact で全体より少し小さい予算だと 1 件も返らず、「今より小さい max_tokens に上げよ」と言う

- 報告: 2026-10-31 / 見た人: BUG-0107 の直す役（補足の欄のページネーションの試験を書いていて見た）
- 見たことだけを書く（調査していない。調査は直す役の仕事）

## 実測

`tests/contract/test_T06_T07_exact_name_supplement.py` の `FILES`（`pkg/a.py#Packer.pack` と、その呼び出し 4 箇所）を
ワークスペース `nm` にし、LSP を起動しない（`structural` の答え。BUG-0107 の変更の影響を受けない経路）で、
`find_references_and_implementations {"target": {"urn": "lk://nm/pkg/a.py#Packer.pack"}, "query_type": "references", "format": "compact", "max_tokens": N}`
を N = 150〜258 で 6 刻みに呼んだ（LSP ありの `exact` の答えでも同じ形）:

```
N=150..246  ヘッダ ~167/Ntok  レコード 0 件
            ! no record fits in max_tokens=N: the next record needs ~22 tokens; raise max_tokens to ~154 or more and call again with the same arguments
N=252       ヘッダ ~251/252tok レコード全部
```

- 全体（前置き + 全レコード）は 251 トークン。1 件目は ~22 トークン。N = 246 でも 1 件も入らない。
- 警告の「raise max_tokens to ~154」は、呼んだ `max_tokens`（例 212・246）より小さい。言われたとおりにしても同じ応答になる。
- 同じ問い合わせの `format: "json"` は、全体より 40 トークン小さい予算で 2 ページに分かれて全部返った（`next_cursor` あり）。

## 原因・直し方・確認（2026-10-31）

直す役（BUG-0110）が調べて直した。

### 原因（2 つ。どちらも `src/lucianke/mcp/budget.py` の `Packer.pack`）

1. **要約の取り分が、先頭の 1 件と `# more:` 行を押し出していた**（afc06fc、BUG-0067 で入った）。
   BUG-0067 の前は、要約つきで 1 件も入らなければ要約（SHOULD）を省いて詰め直していた（「要約（SHOULD）を省けばレコードが
   入るかもしれない」）。これが予算に対して単調でない原因の一つだったので、BUG-0067 はこの詰め直しを外し、代わりに要約の分を
   `min(要約の分, avail // 4)` だけ必ず取り分けるようにした。そのため「前置き + 先頭の 1 件 + `# more:` 行」は入るのに、
   「+ 要約（最大で avail の 1/4）」が入らない予算の帯で 0 件になった。
   - カーソルは base64 で重い（`find_references_and_implementations` のカーソルは 112 文字・71 トークン、`# more:` 行は約 82
     トークン。T-06 の参照 1 行は約 22 トークン）。件数の少ない答えでは「1 件 + カーソル + 要約」が全体とほぼ同じ大きさになり、
     全体の手前の予算がまるごとこの帯に入った。票の実測（全体 251〜252 の手前は全部 0 件）はこれ。
2. **警告の目安が `# more:` 行を数えていなかった**（05aa3ac、BUG-0015 から）。目安は `reserved + 先頭のレコード` で、続きが
   あるときに要る `# more:` 行（カーソル）の分が無い。そのため呼んだ `max_tokens` より小さい値を勧めることがあり、言われた
   とおりに呼び直しても同じ 0 件の応答になった。json も同じ（下の表: 予算 525 で「~510」）。さらに目安はパッカーの見積もりの
   ままで、N で描いた全文を確かめていなかった（N ではヘッダの `~used/max` の桁などで前置きが大きくなりうる）。

疑いのうち、BUG-0078（json の数え方・`shrink_json`）、BUG-0107（`Record.section`）、`mcp/fit.py` の詰め直しのループは
原因ではない。`pack_and_render` の各回の詰めを書き出すと、1 回目の詰めでもう 0 件になっていた（`reserved_tokens` は前置きの
実測のままで増えていない）。compact の 0 件の帯は LSP なしの structural の答えでも、合成のレコード列でも同じに出る。

### 直し方

- `Packer.pack`: 要約の取り分を `min(avail // 4, max(0, avail − F))` にした。F は「先頭のレコードの最も小さい形と `# more:` 行
  （要約なし）」が入るのに要る本文で、予算に依らない（縮退できなければ丸ごと + `# more:`、縮退できれば
  `min(丸ごと + # more:, 縮退版が返る最小の ask + 1 + 再開位置が最大のときの # more:)`）。どちらの項も予算 1 トークンにつき
  高々 1 トークンしか増えないので `avail − 取り分` は予算について減らず、鎖の各形の「収まる」と縮退版の大きさは予算について
  単調のまま（BUG-0067 の単調性を保つ）。先頭の最も小さい形と `# more:` 行が入る予算からは必ず 1 件以上が返る。
  F は取り分が 1/4 より小さくなりうるときだけ求める（縮退 1 回で「1/4 を取っても入るか」を見て、入らないときだけ幅 avail/4 の
  帯を二分探索）。要約の分がある形を初めて数えるときに 1 度だけ求めるので、続きの無い 1 件だけの答えでは縮退の呼び出しは
  増えない。縮退版でページを閉じるときの要約（BUG-0067 の取り分）と、先頭が丸ごと入る予算での形は今までと同じ。
- 1 件も入らないときの目安は `reserved + min(先頭を丸ごと + # more:, 残りの全部)`（残りの全部は具体化していない続きが
  無いときだけ。トレーラなしで全部入る予算。件数の少ない答えでは「1 件 + カーソル」より「全部」のほうが小さい）。値は
  `Page.need_max_tokens` にも入れる。前置きだけで超える警告（BUG-0064）も同じ形にした。
- `mcp/fit.pack_and_render`（5 の段を追加）: 1 件も入らないときは、目安 N で詰めて描き直した全文を数え、警告なしに収まる
  （レコードがあれば 1 件以上入る）まで N を上げてから（最大 6 回）、パッカーに `min_need=N` を渡して警告を書かせる。
  最後に描くのは呼ばれた予算の応答。
- 仕様書 §5.6-4（目安は呼んだ値より大きく、N で呼び直せば 1 件以上が返る。MUST）・§5.6-5（要約の取り分の上限）、
  設計書 §7.2.2 に理由つきで書いた。

- 新しい性質テスト `tests/unit/test_mcp_budget_fit.py`（5 件）: 本物の compact / json のレンダラと `pack_and_render` に、
  乱数のレコード列（大きさ・行数・日本語・group・縮退・途中で切れる版・精度の混在・具体化していない続き・ツールの要約・

  予算以下で申告が数え直しに一致、(2) カーソルは続きがあり 1 件以上のときだけ、(3) 予算に対して単調、(4) 前置き + 先頭 +
  `# more:` 行（か全部）が入る予算なら 1 件以上、(5) 目安は呼んだ値より大きく、目安で呼び直すと警告なしに 1 件以上、を確かめる。
