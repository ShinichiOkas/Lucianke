# S-6 watchfiles の Windows での検知遅延・デバウンス・イベントの届き方

実施日 2026-10-29。Windows 11 Home 10.0.26300（NTFS・ローカルディスク）、CPython 3.12.11、watchfiles 1.3.0（Rust `notify`、Windows は `ReadDirectoryChangesW`）。判定: **合格（ただし `step=10` を指定した場合）**。既定の `step=50` では単発変更の p95 が 100.6 ms で境界に当たる。ほかに設計書 §7.3.6 へ反映する点が 4 つある（下記）。ネットワークドライブは環境が無く**未検証**。

## 確かめたこと
設計書 §7.3.6・§12.1 S-6 と仕様書 §12.4 の想定が、`awatch` で Windows 上で成り立つか。項目番号は `spikes/s06_watch/run.py` の同番号（10 遅延 / 11・14 バースト / 12・17 イベントの種類とフィルタ / 13・15 停止 / 16 CPU）。`awatch` の仕様は `main.py` を読んで確認した: `step` は「新しいパスが増えないまま 1 step 経ったら yield」の間隔、`debounce` は「パスが増え続ける間にグループ化する上限」、`rust_timeout` は無変更のときの Rust 呼び出しの区切り（`None` は Windows 1000 ms / 他 5000 ms、遅延には効かない）。

## 設計への反映（推奨）
1. **§7.3.6 手順 1**: `awatch(ws.root, debounce=1000, step=10, watch_filter=…, stop_event=stop)`。**`step=10` が必須**（既定 50 では p95 が 100 ms 前後）。`WATCH_DEBOUNCE_MS` の意味を「グループ化の最大時間」に改め、値は 1000（仕様書 §12.4 手順 2「50 ms でデバウンス」は「静穏 10 ms で配信、パスが増え続ける間は最大 1 s まで束ねる」に書き直す。NFR-PERF-3 の 500 ms には単発 20 ms で余裕がある）。`stop` は `asyncio.Event` のままでよい。
2. **§7.3.6 手順 3（バースト検知）**: 「1 回のデバウンス窓のパス数 > 500」では**成立しない**。debounce=50 の窓は最大約 170 件、1000 でも 700 ファイルの `git checkout` が [1271, 152] に割れ、遅い checkout はさらに割れる。**窓が 100 件（`BURST_HINT`）以上なら 0.3 秒静まるまで続く窓を合算し、合算が 500 を超えたら `rescan`** に改める（小さい窓は待たず即処理するので単発の遅延は増えない。型は `pattern.py`）。受入の「501 ファイル同時で `rescan` 1 回」はこの規則で通る（自己検査: 700 ファイルで `on_rescan` 1 回・`on_paths` 0 回）。
3. **§7.3.6 手順 4**: **イベント種別を信用しない**。既存ファイルの `os.replace` で `deleted a.py` も届く。種別は捨ててパスの集合に畳み、各パスを `stat` して「存在 → `sha256` 比較」「不在 → removed」と決める（設計書の手順 2「追加 + 削除 = 削除」の畳み込みは**誤り**。`added` と `deleted` が同時に来ても実体は存在しうる）。
4. **§7.3.6 手順 4 にディレクトリ規則を追加**: ディレクトリの移動・改名は**子のイベントが来ない**。パスがディレクトリなら `os.walk` で子を列挙して取り込み（`pattern.py` の `resolve`）、パスが不在なら `files.path` の前方一致 `パス + '/'` の行も removed にする（`git checkout` / ブランチ切替で消えた・移された配下の取りこぼし防止）。
5. **§7.3.6 手順 1 のフィルタ**: `.git/`、EditTransaction の一時名（`.lucianke-tmp-*`）はフィルタで落とせる（`expect()` が対象にするのは最終パスのイベントだけになる）。`.git/HEAD` の変更でブランチ切替を直接拾いたいなら、フィルタで `.git/HEAD` だけ通す（MAY。作業ツリーのファイル変更からも検知できる）。
6. **§7.3.6 手順 6・§12.1 S-6 行**: 監視の開始失敗は例外（存在しないパスで `FileNotFoundError`）で表れるので `try/except OSError` で `mode="polling"`（遅延検証）へ切り替える。`force_polling` は取りこぼしがあるため使わない。**ネットワークドライブは未検証**として残し、S-6 の代替策（遅延検証）はそのまま。
7. **§7.3.6 起動順**: `awatch` を `create_task` してイベントループを 1〜2 回譲った後に差分索引（§7.6.5）を始めれば、起動時の隙間は生じない。

## 使うコードの型
全文と自己検査は `spikes/s06_watch/pattern.py`（`python spikes/s06_watch/pattern.py`）。単発 30 回 p50 16.7 / p95 21.4 ms、700 ファイルで `rescan` 1 回、停止 5 ms を確認済み。

```python
STEP_MS, DEBOUNCE_MS, BURST_HINT, BURST_QUIET_S, WATCH_BURST_FILES = 10, 1000, 100, 0.3, 500

async def pump(root, q, stop):                       # 監視ループ。種別は捨ててパス集合にする
    async for changes in awatch(root, debounce=DEBOUNCE_MS, step=STEP_MS,
                                watch_filter=make_filter(root), stop_event=stop):   # .git/ と .lucianke-tmp-* を落とす
        q.put_nowait({os.path.relpath(p, root).replace("\\", "/") for _, p in changes})
    q.put_nowait(None)                               # stop.set() で終わる（1〜48 ms）

async def consume(q, on_paths, on_rescan):           # デバウンス窓内の畳み込みとバースト検知
    while (paths := await q.get()) is not None:
        ended = False
        while len(paths) >= BURST_HINT:              # 大きい窓だけ、0.3 秒静まるまで合算
            try: nxt = await asyncio.wait_for(q.get(), BURST_QUIET_S)   # キューの get のキャンセルは安全
            except TimeoutError: break
            if nxt is None: ended = True; break
            paths |= nxt
        await (on_rescan() if len(paths) > WATCH_BURST_FILES else on_paths(paths))
        if ended: return
        # on_paths: resolve(root, paths) -> (現存, 消えた)。ディレクトリは os.walk で展開、消えたパスは前方一致でも削除
```

`awatch` を `wait_for` で包んで期限を付けてはならない（キャンセルで監視が終わる）。期限が要るときは上のようにキューを挟む。

## 再現手順
```
.venv/Scripts/python.exe spikes/s06_watch/run.py          # 項目 10〜17 すべて（約 2〜3 分）
.venv/Scripts/python.exe spikes/s06_watch/run.py 10 15    # 番号を指定
.venv/Scripts/python.exe spikes/s06_watch/pattern.py      # 型の自己検査
```
一時ディレクトリは `%TEMP%` 配下に作り、終了時に消す（リポジトリには書かない）。時間は `time.perf_counter()`。項目 14 は `git` が PATH にあること。値は 1 回の実測で、環境（ウイルス対策・ディスク負荷）により数 ms 動く。`step=50` の p95 は debounce=50 の行で 100.6 ms、debounce=1600 の行で 52.4 ms（max 101.2）と、遅延が 50 ms と 100 ms の二峰に分かれるため p95 が境界をまたぐ。境界上の値として扱う。
