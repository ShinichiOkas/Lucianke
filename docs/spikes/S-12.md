# S-12 トークン推定の較正（TokenEstimator と o200k_base）

実施日 2026-10-29。Windows 11 Home 10.0.26300、CPython 3.12.11、tiktoken 0.14.0（`uv run --with` の一時利用。pyproject は未変更）。判定: **現行の係数は不合格**。日本語 Markdown が −16〜−17%、compact 出力が −11%、base64 などの塊が −43〜−63% で、いずれも**過小**（実測が予算を超える向き）。文字種を細かくして「連の数」を数える式（`lean_wide`、8 項）に替えると、全種類の合計誤差が ±3.3% 以内（交差検証の保持側）に収まる。

## 確かめたこと
`TokenEstimator.count`（現在は `src/lucianke/core/tokens.py`。budget.py は再公開）と `o200k_base` のトークン数の比を、ファイル単位と種類単位で取った。コーパスは `src/`・`tests/` の Python、`docs/*.md`（日本語中心）、`docs/spikes/*.md`、`tests/fixtures/poly/` の全ファイル、仕様書の compact 出力例 26 ブロック（§6.1.1・§11）と json/sql の例、合成の base64 と SHA-256 hex。係数は非負最小二乗（相対誤差、種類ごとの重みをそろえる）で当てはめ、ファイル単位 2 分割の交差検証で保持側の誤差を見た。1 ファイルしかない種類（ipynb と合成 2 種）は標本内の誤差。再現は `bench/tokens/calibrate.py`。

## 結果
誤差は `推定 / o200k_base − 1`。「合計」は種類の全トークンの合計、「平均」はファイル単位の絶対誤差の平均、「最大」は 1 ファイルの最大（50 トークン未満は除く）。合否は合計と平均がともに ±10% 以内。提案は交差検証の保持側。

| 種類（n） | 現行 合計 | 現行 平均 | 現行 最大 | 提案 合計 | 提案 平均 | 提案 最大 |
|---|---|---|---|---|---|---|
| Python src（71） | +7.7% | 7.7% | +19.8% | +0.2% | 2.8% | 10.3% |
| Python tests（48） | +6.9% | 7.6% | +19.2% | +1.2% | 3.0% | 12.3% |
| docs/*.md 日本語（3） | **−16.0%** | **15.2%** | 17.1% | −0.1% | 2.6% | 5.2% |
| docs/spikes（10） | **−17.3%** | **18.3%** | 30.2% | −2.8% | 3.4% | 9.2% |
| poly コード（12） | **+11.5%** | **12.3%** | 26.2% | −2.3% | 4.9% | 11.5% |
| poly 設定・データ（7） | −0.8% | **10.7%** | 17.2% | +0.5% | 2.6% | 3.4% |
| poly 文書（5） | −6.6% | **12.5%** | 16.7% | +2.0% | 5.1% | 10.9% |
| spec の json/sql 例（11） | **+13.7%** | 8.3% | 20.1% | −3.3% | 5.8% | 12.5% |
| **compact 例（26）** | **−11.3%** | **11.8%** | 32.0% | −0.9% | 5.4% | 16.2% |
| ipynb（base64 PNG 13.6 KB, 1） | **−43.1%** | — | — | −3.6%（標本内） | — | — |
| 合成 base64 / hex（各 1） | **−62.5% / −57.2%** | — | — | −8.9% / +7.0%（標本内） | — | — |

- 現行の 4 分類のまま係数だけ再当てはめしても通らない（py_src +10.7%、poly コード +23.2%、spec の sql +23.9%、ipynb −34.8%）。分類が粗いのが原因で、ASCII は文字数ではなく**語の数**で、空白と記号は**連**でトークンになる。表の細分化（設計書 §12.1 S-12 の代替）だけでは足りず、連の数が要る。
- compact を 1 行ずつ数えて足すと（パッカーの数え方）現行 −10.9%、提案 −1.6%（行間の改行を数えない分だけ約 0.7pt 下がる）。
- 速度（1 MB の文字列、7 回の最小値、他の役が並行して走る環境）: 現行 66〜73 ms、提案 150〜200 ms（約 2.3〜2.8 倍）、参考 tiktoken 110〜145 ms。パッカーは予算に達するまでしか数えない（8 KB なら約 1.5 ms）ので影響は小さい。

## 設計への反映
`core/tokens.py`（budget.py）の担当への依頼。項の定義は `bench/tokens/coefficients_proposal.json`、実装の型は `calibrate.py` の `fast_estimator`（式と全コーパスで一致を確認）。

1. **推定式を `lean_wide` に替える**（設計書 §7.2.1・仕様書 §5.7 の「文字種別の係数」を「文字種別と連の数の係数」に改める）。トークン数 = 切り上げ（Σ 係数 × 数）。係数は 1/100 刻みの有理数で、整数演算にできる（分母 100）。置き場は設計書どおり `tokens.toml`。
   - `blob_chars` 0.63: `[A-Za-z0-9+/=]{40,}` の文字数（base64・SHA-1/256 の hex）。**先に数えて本文から除く**。
   - `letters_runs` 0.85: `[A-Za-z]+` の個数。`digits_chars` 0.90: `[0-9]` の文字数。`symbol_runs` 0.87: ASCII 記号 `` [!-/:-@\[-`{-~]+ `` の連の個数。
   - `space_runs_multi` 0.92: `[ \t]{2,}` の個数（インデント）。単一の空白は 0（語に吸収される）。`nl_chars` 0.60: `\r` と `\n` の文字数。
   - `wide` 0.95: 仮名・漢字・全角記号の文字数。範囲は U+3000–30FF、U+31F0–31FF、U+3400–4DBF、U+4E00–9FFF、U+F900–FAFF、U+FF00–FFEF、U+20000–2FA1F。
   - `other` 0.46: 上記のどれでもない文字の個数（ASCII 以外の記号・制御文字・ハングルなど）。
2. 現行の `ascii_word` 1/4・`ascii_symbol` 1/2・`wide` 1/1.5 は捨てる。「全角 1.5 文字で 1 トークン」は日本語で −16% の主因。
3. **速度**: ASCII だけの文字列は `wide` の走査を省く（`text.isascii()`）。1 MB で現行の約 2.5 倍だが、パッカーは予算までしか数えないので許容。
4. **安全側**: 推定が実測より小さいと、実測が `max_tokens` を超える。提案の保持側の合計の最悪は −3.3%（base64 は −8.9%）。余裕を持たせるなら全係数を ×1.03 にする（任意。誤差の符号を + 側へ寄せる）。
5. **代案**（連を数えたくない場合）: 文字種のみ 10 項の `split_chars`（`letters_chars` 0.21、`digits` 1.17、`space_chars` 0.14、`nl` 0.46、`symbol_chars` 0.47、`kana` 0.93、`kanji` 0.62、`cjkpunct` 1.85、`other` 0.38、`blob` 0.63）。交差検証は合格だが、poly 文書の平均 10.0%・spec の sql の平均 8.9% と余裕がなく、全角記号の係数は実測の限界費用（約 0.8）と合わない。非推奨。
6. **単体テスト**: tiktoken なしで、固定の文字列と基準トークン数（`result.json` の仕様書の compact 例など）を `tests/unit` に置き、推定との比が ±10% に入ることを確かめる。陽性対照に現行の係数が落ちることも。
7. **限界**: 当てはめ標本は本リポジトリ（日本語コメントの Python が多い）に偏る。poly フィクスチャは合計 3 KB 程度で小さい。TS・Go・Rust・韓国語（`other` 扱い）は未検証。M1 のベンチ（`bench/run_bench.py`）で較正を再実行し、種類別の合計誤差が ±10% を超えたら失敗にする。

## 再現手順
```
cd S:\work\develop\Lucianke
set PYTHONUTF8=1
uv run --no-project --with tiktoken --with numpy --with scipy python bench/tokens/calibrate.py
```
`bench/tokens/result.json`（種類別とファイル別の誤差、候補 6 種の係数と交差検証、速度）と `coefficients_proposal.json`（提案の項・正規表現・期待誤差）を書く。tiktoken は初回に語彙を取得するためネットワークが要る。`src/` と `tests/` は他の役が並行して書き換えるので、数値は実行のたびに少し動く（コーパスの指紋を `result.json` に記録）。

## 反映（2026-10-29）
- 採用式: `core/tokens.py` の `TokenEstimator.count` を `lean_wide`（8 項: 英字の連 0.85・数字 0.90・記号の連 0.87・2 個以上の空白の連 0.92・改行 0.60・全角 0.95・その他 0.46・塊 `[A-Za-z0-9+/=]{40,}` 0.63。単一の空白は 0、塊は先に数えて本文から除く、分母 100 の整数演算で切り上げ）に替えた。係数表は `TOKEN_COEFFICIENTS`（旧名 `TOKENS_PER_CHAR` は別名で残す）。
- 回帰テスト: `tests/unit/test_core_tokens_calibration.py` が `result.json` の `o200k_base` 基準（本文の文字数が記録と一致する標本のみ）で種類ごとの合計誤差と平均誤差 ±10% を検査（tiktoken 不要）。結果は全種類合格: 合計 compact -0.8%・日本語 md -0.1%・spikes -2.9%・poly コード -1.1%・ipynb -3.6%・py_src +0.5%・合成 base64 -8.3%・hex +7.7%（旧式は -11.3%・-16.0%・-17.3%・+11.5%・-43.1%・-62.5%・-57.2%）。旧式を陽性対照に置き、落ちることも確かめる。
- 速度（1 MB、7 回の最小値）: py_src 126 ms、日本語 md 148 ms、compact 188 ms（旧式の約 2.3〜2.8 倍。S-12 の実測 150〜200 ms と一致）。
- 副作用の修正: 改行の係数が 0.25 から 0.6 に上がったため、パッカーが各行の終端の改行を数えるようにした（`mcp/budget.py`。レコード別の和が応答全体の推定以上になる）。縮退には終端の改行の分（1）を引いた予算を渡す。`tools/_services.py` の `estimate_tokens`（独自の粗い式）はパッカーと同じ推定器にした。
- 見送り: 余裕を持たせる全係数 ×1.03（任意）は入れていない。合成 base64 が -8.3% と ±10% に近いので、M1 のベンチ（`bench/run_bench.py`）で再較正し、TS・Go・Rust・韓国語を標本に加える。設計書 §7.2.1 と仕様書 §5.7 の「文字種別の係数」の文言は未更新（「文字種別と連の数」に改める）。
