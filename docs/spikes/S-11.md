# S-11 LSP ごとの位置の単位（UTF-8 / UTF-16）と LineIndex の一致

実施日 2026-10-29。Windows 11 Home 10.0.26300、CPython 3.12.11、Node v25.2.1。basedpyright 1.40.2、ruff 0.17.3、vtsls 0.3.0（typescript 6.0.3）、typescript-language-server 6.0.2（以下 tsls、代替の確認用）。判定: **合格**（4 サーバーの単位がすべて分かり、`LineIndex` の変換で全件一致。`LineIndex` に誤りは無かった）。ただし設計書の 2 点を直す（下記）。

## 確かめたこと
- `initialize` で `positionEncodings` を 5 通り（`[utf-8,utf-16]` / `[utf-16]` / 提示なし / `[utf-8]` / `[utf-32,utf-8,utf-16]`）で送り、返る `positionEncoding`（無いことも 1 つの値として記録）を表にした。
- フィクスチャは 5 つの識別子（BMP のみ `あいう` の後ろ、サロゲートペア `😀` の後ろ、前合成 `é`、結合文字 `e+U+0301`+`😀`+`あ`、識別子そのものが `名前`）を、定義側と使用側の両方で全角・絵文字の **後ろ** に置いた。3 つの単位で列が全部違うので、返り値から単位が一意に決まる。判定は「範囲を各単位で読み、識別子の文字列になる単位」（`lsp_probe.cp_from_col`。`LineIndex` に依存しない）。
- `hover`（range）/ `definition` / `references` / `rename`（編集をバイト列へ適用して期待本文と比較）/ `publishDiagnostics` を測った。ruff は定義系を持たない（hover は `# noqa` のみ）ので、**診断（F821・F541）の範囲で代替**した。
- `LineIndex` との一致: 受信（サーバーの列 → `from_unit` → コードポイント）と送信（コードポイント → `to_unit` → 列）が、独立計算 `col_in` と一致するか。`rename` の編集は `from_unit` → `position_to_offset` でバイト列に適用し期待本文と一致するか。`LineIndex` の網羅検査（43 行・1,110 位置 × 3×3 の単位の組み、文字の途中の丸め、行末超過、LF / CRLF / BOM+CRLF のオフセット往復）。本文は `didOpen` に送った文字列そのものから `LineIndex` を作った。
- 送る側の単位違い: 隣り合う短い識別子 7 個（`row = ("😀😀😀", aa, bb, …, gg)`）への hover を 3 つの単位の列で送る。増分 `didChange` で不正な識別子の先頭に `X` を挿入し、診断メッセージの名前（`Xundefined_name_zz` か）で判定する。

## 結果
| サーバー | 提示 `[utf-8,utf-16]` | `[utf-16]` | 提示なし | `[utf-8]` | `[utf-32,utf-8,utf-16]` | 実測の単位 |
|---|---|---|---|---|---|---|
| basedpyright 1.40.2 | 無し | 無し | 無し | 無し | 無し | **UTF-16** |
| vtsls 0.3.0 | 無し | 無し | 無し | 無し | 無し | **UTF-16** |
| tsls 6.0.2 | 無し | 無し | 無し | 無し | 無し | **UTF-16** |
| ruff 0.17.3 | **utf-8** | utf-16 | utf-16 | **utf-8** | **utf-8** | 返した値どおり |

「無し」は `positionEncoding` が応答に無い（= LSP の既定の UTF-16）。utf-8 を提示しても basedpyright・vtsls・tsls は採らない。utf-32 を先頭に提示しても ruff は採らず utf-8 を選ぶ。

返り値の例（`s_astral = "😀"; v_astral = 2` の `v_astral`。コードポイント 16 / UTF-16 17 / UTF-8 19）: basedpyright の hover・definition・references はすべて 17（UTF-16）。`名前` の使用側（`("😀日本語", 名前)`）はコードポイント 19 / UTF-16 20 / UTF-8 28 で、返りは 20。ruff の F821（`bad = "😀日本語" + undefined_name_zz`）は utf-8 交渉で 24、utf-16 交渉で 16（コードポイント 15）。

| 項目 | 結果 |
|---|---|
| `LineIndex` 受信（列 → コードポイント） | basedpyright・vtsls・tsls 各 21/21、ruff 2/2（utf-8 交渉・utf-16 交渉の両方）一致、丸め（clamped）なし |
| `LineIndex` 送信（コードポイント → 列） | 各 11/11、ruff 2/2 一致 |
| `rename` の編集をバイト列へ適用 | basedpyright・vtsls・tsls 各 5/5 で期待本文と一致（`from_unit` → `position_to_offset`） |
| `LineIndex` 網羅検査 | 不一致 0。文字の途中は直前の境界に丸めて `clamped=True`、行末超過も `clamped=True`、オフセット往復 415 位置 × 3 形式（LF / CRLF / BOM+CRLF）で不一致 0 |
| 送る側の単位違い（UTF-16 の 3 サーバー、結果は同一） | hover を UTF-8 の列で送ると 7 個中 **別のシンボル 6・null 1・正解 0**（`aa→bb`、`bb→cc` …）、コードポイントの列でも 別のシンボル 6・null 1。**エラーは返らない**。増分 `didChange` に UTF-8 の列を送ると 8 列後ろに `X` が入り（`undefineXd_name_zz`）、コードポイントの列では 1 列手前に入って構文エラーになる。どちらも黙って成功する |
| 送る側の単位違い（ruff、utf-8 交渉） | UTF-16 の列で増分 `didChange` を送ると、列が `日本語` の文字の途中に当たる場合 **ruff がパニックして終了（exit 101、`start of range should be a character boundary`）**。境界に当たる列なら無事（`ruff_midchar.py` で再現、対照あり） |
| サロゲートペアの途中の列への hover | 3 サーバーとも null、エラーなし（文字列リテラル内で、情報としては弱い） |
| 後始末 | 全サーバーが `shutdown` → `exit` → 終了コード 0（ruff は上記パニック時を除く）。vtsls・tsls の子 `node` は 1.5 秒後に残らず。basedpyright の子 `node` が 1.5 秒後に 1 回だけ残った（10 回中 1）→ 後から消えると見込まれるが、§6.5 の kill は木ごとにする |

副次の発見: **vtsls の `definition` は識別子ではなく宣言文全体（`export const vAstral = 2;`）の範囲を返す**（開始列は UTF-16 で正しい）。tsls は識別子の範囲。S-5 の結果と合わせ、定義の「名前の範囲」が要る場面は hover / documentSymbol で取る。

## 設計への反映（推奨）
1. **§7.5.1 `position_encoding_default` は持たない（削除）。** 規則は 1 つで足りる: `unit = Unit(caps.get("positionEncoding", "utf-16"))`。実測した 4 サーバーのうち、応答に無いものは全部 UTF-16 で、サーバーごとの上書きが要る例は無かった。上書きを持つと、誤った値が黙って位置を壊す穴になる。代わりに「期待する単位」を契約テスト（`tests/lsp_contract`、サーバー未導入なら skip）に持たせ、サーバーの更新で単位が変わったら落とす。
2. **§7.5.3 `LspClient.encoding: Literal["utf-16","utf-8"]` を `Unit` にする。** 未知の値（`utf-32` を含む。提示していないので来ないはず）は UTF-16 に倒して警告ログ。
3. **提示は仕様どおり `["utf-8","utf-16"]` のまま推奨。** 実測で utf-8 を採るのは ruff だけで、変換は同じ `LineIndex` の呼び出し（単位が違うだけ）。utf-8 の経路は rust-analyzer・clangd などの将来のサーバーでも通るので、ruff で常時検査しておく価値がある。逃げ道として設定（例 `lsp.position_encodings`）で `["utf-16"]` に絞れるようにする。
4. **境界の列だけを送る（MUST）。** `to_unit` が出す列は常に文字境界なので守られる。丸め（`clamped=True`）が出たときは要求を送らず降格応答にする（ruff は文字の途中でパニックする。UTF-16 の 3 サーバーは黙って別の場所を指す）。`didChange` が全文（ADR / §7.5.4）なので、クライアント → サーバーの位置は要求（definition・references・hover・rename・codeAction の range）だけに限られる。増分 `didChange` を入れる（MAY）ときは境界検査を必須にする。
5. **§12.2 の受入**（全角・絵文字・結合文字を含む行で位置が一致し、`rename_symbol` が正しい範囲を書き換える）は 4 サーバーで満たされた。この検査をそのまま契約テストにする。
6. **未測定**: rust-analyzer・gopls・clangd。`rust-analyzer` は rustup のシムだけで本体が未導入（`Unknown binary 'rust-analyzer.exe'`）、gopls・clangd は PATH に無い。`run_s11.py` と `fixture_rs/` は rust-analyzer 用の枠まで用意した（未検証）。

## 使うコードの型
```python
from lucianke.core.model import Position
from lucianke.core.textpos import LineIndex, Unit

OFFER = ["utf-8", "utf-16"]                       # initialize: capabilities.general.positionEncodings
unit = Unit(init_result["capabilities"].get("positionEncoding", "utf-16"))   # 無ければ UTF-16。未知なら UTF-16 + 警告

def to_lsp(idx: LineIndex, pos: Position) -> dict | None:
    (line, col), clamped = idx.to_unit(pos, unit)         # idx は didOpen / didChange に送った本文から作る
    return None if clamped else {"line": line, "character": col}   # 丸めが出たら送らず降格

def from_lsp(idx: LineIndex, p: dict) -> Position:
    return idx.from_unit(p["line"], p["character"], unit).value    # 内部表現は 0 始まりのコードポイント
```

## 再現手順
```
uv run python spikes/s11_posenc/run_s11.py --lineindex            # LineIndex の網羅検査（サーバー不要）
uv run python spikes/s11_posenc/run_s11.py basedpyright           # ruff / vtsls / tsls も同様。1 サーバー約 80 秒（ruff は約 3 分）。結果は out/s11_<名前>.json
uv run python spikes/s11_posenc/ruff_midchar.py mid               # ruff のパニック再現（boundary が対照）
```
複数サーバーを 1 プロセスで `asyncio.gather` すると止まることがあったので、サーバーごとに別プロセスで走らせる。フィクスチャは実行時に `fixture_*/` へ書き出される（エスケープで定義。絵文字は U+1F600、`é` は前合成 U+00E9）。
