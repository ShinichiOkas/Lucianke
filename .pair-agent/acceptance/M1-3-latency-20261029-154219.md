# M1-3 レイテンシの受入（仕様書 §14.4、NFR-PERF-1、2026-10-29）

## 2026-10-31 追記: 判定の形が変わった（仕様書 §17 OD-23 の決定 (b)）

この報告は変更前の判定（成功かつ非降格の全呼び出しで p95 < 50 ms）で書いた。2026-10-31 に OD-23 を (b) に決め、§3.2 NFR-PERF-1・§14.4・§15.2 M1-3 を
次の形に直した。M1-3 の受入はこの形でやり直す（`bench/run_latency.py` が冷・温に分けて判定し、結果 JSON のツールごとの `cold` / `warm` に載せる）。

- **LSP の `exact` 経路（T-06・T-07・T-08）**: 母集団を **冷**（そのツールがその実行で初めて聞いた対象。台本の探り・準備の呼び出しで聞いた対象は
  「聞いた」に数える）と **温**（2 回目以降）に分ける。冷は p95 < 1 秒（深さ 2 以上の T-07 は < 2 秒。台本の T-07 は depth 2）、温は p95 < 50 ms。両方を
  満たして合格（どちらかの母集団が 0 件ならその側は判定しない）。
- **それ以外の Fast Path のツール**: 今までどおり全呼び出しの p95 < 50 ms。
- 理由: 冷えた `exact` の下限は LSP そのもので 50 ms に入らず、入れるには全シンボルを先に取るしかないが、目印はどのファイルの変更でも外れるので
  ベンチの数字を作るだけになる。全呼び出しを 1 つの母集団にすると、温冷の比が台本の対象の選び方で決まる（200 回のうち初めての対象は F-PY 約 170、
  F-TS 約 20）。

参考: この報告の run2（`bench/results/20261029-154219-windows-latency.json`）を新しい形で集計し直すと（p95 ms、冷 / 温）、T-06 は F-PY 467 / 30・
F-TS **2388** / 15、T-07 は F-PY 952 / **200**・F-TS 788 / **765**、T-08 は F-PY 569 / 19・F-TS 937 / **1140**（太字が不合格）。新しい形での受入の

## 判定: **不合格**（M1-3 を満たさない）

不合格の項目:

1. **T-06 `find_references_and_implementations`、T-07 `query_call_hierarchy`、T-08 `get_diagnostics` が、F-PY・F-TS の両方で Fast Path の p95 < 50 ms を超えた**（2 回の計測とも）。サーバー内 `timing_ms` の p95（ms、run1 / run2）: T-06 は F-PY 551 / 454、F-TS 333 / 292。T-07 は F-PY 842 / 883、F-TS 1024 / 765。T-08 は F-PY 332 / 333、F-TS 1015 / 937。p50 は T-06・T-08 が 8〜14 ms で、尾（T-06 の p99 は 1.2〜2.5 s、T-07 は最大 5 s 級）が p95 を押し上げている。
2. **14 ツールのうち 5 本（T-00、T-01、T-10、T-11、T-13）が計測されていない。** `bench/run_latency.py` の台本（`PLANS`）が 9 ツールだけで、残り 5 本は `tools/list` に載っていても計画が無く、結果 JSON の `m1_3_by_tool` に `not_implemented` と記録される（実際には実装済み）。M1-3 は「14 ツール」で判定するので、現状は 14 ツールでは判定できない。
3. （参考。F-POLY は §14.4 の母集団外）F-POLY の T-07 は p95 401 / 408 ms で不合格。F-POLY の T-08 は 200 回すべて降格応答（`structural`、LSP は `unavailable`）で、判定する母集団が 0 件。

合格したツール（F-PY・F-TS の 2 回とも p95 < 50 ms）: T-02、T-03、T-04、T-05、T-19、T-20。

## 計測の条件

- 台本: `bench/run_latency.py --fixtures poly,F-PY,F-TS --calls 200`（サーバーは `python -P -m lucianke`、stdio、`format: json`、シード 20261029、計測外の準備呼び出しを 5 回）。母集団は成功かつ `is_degraded == false`、判定はサーバー内 `timing_ms`。ウォームアップは LSP が ready で索引ジョブが終わるまで待ち、所要は報告値（合否に使わない）。
- 作業ツリー: push 済みの `origin/main` の使い捨て作業ツリー（dirty なし）。run1 は `5225ec1`、run2 は計測中に進んだ最新の `605e79b`（T-06・T-07 の LSP exact 経路、T-08 の変更を含む）。フィクスチャ: F-PY = httpx `b5addb64`、F-TS = ky `35418888`（本体の `bench/.cache/` を共有）。F-TS の LSP は typescript-language-server（一時ディレクトリに npm で入れ、終わったら片付けた）、F-PY は basedpyright。
- 機材: AMD Ryzen Threadripper 3960X（48 論理）/ 63.9 GB / Windows 11。
- **負荷**: この計測の間も他の役が並行して動いており、システム全体の CPU は run1 が平均 26.2%・最大 53.5%、run2 が平均 23.7%・最大 41.7%（1 秒間隔）。50% を超えたのは run1 の 1 秒（15:38:24、53.5%）だけで、他に 50% 超の時間帯はない。したがって「CPU 50% 超の負荷あり」の区間はほぼ無いが、機材が空いていたわけでもない（48 論理のうち常に 11〜12 コア分は他の役が使っていた）。完全に空いた状態での再計測はできていない。run1 と run2 で合否も各ツールの p95 の桁も一致しており、負荷による揺れは判定を変えていない。
- stdout の純度と子プロセスの監視（§14.2）は 3 フィクスチャ × 2 回とも違反なし。サーバーのエラーログ行（ERROR / Traceback）は 0 件。
- 失敗した呼び出し（母集団から除外、両 run で同数）: F-TS で `E_TARGET_AMBIGUOUS`（T-04 20 件、T-05 15 件、T-06 23 件、T-07 33 件。200 回中）、F-PY の T-07 で `E_UNSUPPORTED` 13 件、F-TS の T-08 で `E_TIMEOUT` 1 件（run1 のみ）。
